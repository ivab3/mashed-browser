# Mashed: Fully Loaded — browser revival roadmap

Статус: рабочая версия v0.4

Цель документа: удерживать техническое направление, границы проекта и измеримые критерии готовности.

## 1. Цель проекта

Создать браузерную реализацию Mashed: Fully Loaded, сохраняющую главное ощущение оригинала:

- локальные заезды для 1–4 игроков;
- общую камеру, удерживающую игроков в кадре;
- выбывание от отрыва от лидера и края экрана;
- аркадную физику машин;
- оружие, усиления и разрушаемые объекты;
- оригинальные трассы, машины, звук и визуальный стиль, когда пользователь предоставляет собственные игровые данные.

Мы не пытаемся запускать `MFL.exe` в браузере и не стремимся к побайтовой декомпиляции. Мы создаём новый движок, который читает или конвертирует оригинальные ресурсы и воспроизводит поведение игры.

## 2. Принятые решения

### Основной стек

- TypeScript в строгом режиме.
- Vite для разработки и сборки.
- Three.js как слой рендеринга.
- Rapier 3D (`@dimforge/rapier3d`) для физики.
- WebGL2 как обязательный графический backend.
- WebGPU — возможная поздняя оптимизация, не зависимость MVP.
- Web Audio API для звука.
- Gamepad API и клавиатура для локального мультиплеера.
- Vitest для модульных тестов.
- Playwright для браузерных и визуальных smoke-тестов.

### Продуктовые ограничения первой версии

- Desktop-браузеры прежде мобильных устройств.
- Локальный мультиплеер прежде сетевого.
- Одна общая камера прежде split-screen.
- Точное ощущение управления важнее полного совпадения графических эффектов.
- Оригинальные игровые данные не коммитятся в репозиторий.
- Разработка сначала использует локальный CLI-экстрактор; импорт `.bin/.cue` непосредственно в браузере появится позднее.

### Принцип совместимости с оригиналом

Проект разделяется на две части:

1. Свободно распространяемый браузерный движок и инструменты.
2. Пользовательские данные, извлекаемые из принадлежащего пользователю образа или установленной игры.

До получения отдельных прав проект не должен публиковать оригинальные EXE, модели, текстуры, музыку, речь или видеоролики.

## 3. Предлагаемая архитектура

Ориентировочная структура после bootstrap:

```text
apps/
  web/                  браузерная игра и UI
  asset-viewer/         просмотр DFF/TXD/BSP и отладка материалов
packages/
  assets/               PIZ/RWS/RenderWare readers и manifest
  core/                 игровой state, правила, fixed-step loop
  input/                клавиатура, Gamepad API, remapping
  physics/              адаптер Rapier и модель автомобиля
  renderer/             Three.js сцена, материалы, эффекты
  audio/                события звука и Web Audio runtime
  replay/               запись input frames и проверки детерминизма
tools/
  extractor/            BIN/CUE → ISO → InstallShield → PIZ/RWS
  converter/            DFF/TXD/BSP/RWS → web-ready assets
game-data/              локальные извлечённые данные, всегда ignored
```

Ключевое правило зависимостей:

```text
input ──> core ──> physics
           │          │
           ├──> audio │
           └──> renderer <── assets
```

`core` не должен зависеть от DOM или Three.js. Это позволит запускать симуляцию в тестах, воспроизводить реплеи и в будущем вынести её в Worker.

## 4. Этапы и контрольные точки

Оценки ниже предполагают одного опытного разработчика full-time. Для part-time их разумно умножать на 2–3. Это ориентиры, а не обещанные сроки.

Прогресс и протокол измерений: [REFERENCE.md](./REFERENCE.md).

Задачи:

- [x] Запустить оригинал в совместимой Windows-среде без `launch.exe`.
- [x] Провести многочасовой ручной compatibility/smoke-test оригинала.
- [x] Зафиксировать сценарии ручной приёмки управления, камеры, столкновений, оружия и выбывания.
- [x] Составить каталог трасс, машин, режимов и языков.
- [x] Зафиксировать границы распространения оригинальных данных для разработки.

Критерий готовности:

- Есть воспроизводимый запуск оригинала и подтверждённый ручной baseline совместимости.
- Есть `REFERENCE.md` со сценариями будущей приёмки и нормализованный каталог контента.

  сравнение не является обязательным условием этапа или браузерной версии.

### Этап 1. Воспроизводимое извлечение ресурсов — 1–2 недели

Реализация: [`tools/extractor`](./tools/extractor/README.md). Метаданные выбранных fixtures:
[`reference/extraction-fixtures.json`](./reference/extraction-fixtures.json).

Задачи:

- [x] Автоматизировать чтение MODE1/2352 `.bin/.cue`.
- [x] Извлекать ISO 9660 и InstallShield CAB без установки игры.
- [x] Реализовать или адаптировать чтение `PIZ` и `RWS`.
- [x] Генерировать manifest: путь, тип, размер, hash и происхождение файла.
- [x] Поддержать источник в виде образа и уже установленной директории.
- [x] Добавить защиту от случайного коммита `game-data/`.

Целевой интерфейс:

```bash
pnpm extract --source "/path/to/game.cue" --out ./game-data
pnpm assets:inspect --manifest ./game-data/manifest.json
```

Критерий готовности:

- Одна команда извлекает `MFL.exe`, все `PIZ/RWS` и открытые файлы.
- Повторный запуск даёт те же hashes.
- Автоматически находятся как минимум одна машина, одна трасса, Lua-скрипт, звук и видео.

Gate A — продолжать проект только если extraction полностью воспроизводим.

Статус 2026-08-23: **Gate A пройден** на эталонном образе. Два последовательных запуска
из CUE дали одинаковый SHA-256 manifest
`e5dac84fbe7ba75adbddbf2e1c74c0e367f5e11d9b4085ddd6526a70b4c48a0c` и нашли 226
исходных файлов плюс 1610 PIZ entries. Отдельно проверен источник установленной директории;
ключевые hashes `MFL.exe`, `Wildfire.piz` и `Warzone.piz` совпадают между обоими путями.

### Этап 2. Asset spike: машина и трасса — 2–4 недели

Это главный технический риск проекта, поэтому он идёт до игрового UI и меню.

Прогресс и технические наблюдения: [reference/ASSET_SPIKE.md](./reference/ASSET_SPIKE.md).

Задачи:

- [x] Извлечь внутреннее содержимое одного архива машины и одной трассы.
- [x] Загрузить DFF-модель машины и TXD-текстуры.
- [x] Определить RenderWare coordinate system, scale, winding и material flags.
- [x] Разобрать `GRAPHICS.BSP` хотя бы до вершин, индексов, материалов и текстур.
- [x] Разобрать `COLLIDE.BSP` до статической collision mesh.
- [x] Проверить DXT/palette/alpha-варианты текстур.
- [x] Сделать отдельный asset viewer с сеткой, осями, wireframe и выбором chunks.
- [x] Решить, читаем ли форматы в runtime или конвертируем заранее в glTF/KTX2/custom binary.

Критерий готовности:

- В браузере отображается узнаваемая машина с корректными текстурами.
- Одна трасса визуально совпадает с оригиналом.
- Collision mesh накладывается на видимую геометрию без систематического смещения.
- Asset viewer загружает файлы повторяемо и сообщает понятные ошибки.

Gate B:

- Если BSP разбирается — продолжаем с оригинальными трассами.
- Если BSP остаётся непрозрачным — отдельно оцениваем ручной конвертер, анализ загрузчика в `MFL.exe` или пересборку трасс. До решения не расширяем игровой код.

Статус 2026-08-23: **Этап 2 и Gate B завершены**. Graphical и collision BSP разбираются и
совмещаются; coordinate/scale/winding, material/MatFX semantics и texture variants закреплены в
reader и viewer. Проверены все 78 TXD: PC palette4/palette8/RGBA32 декодируются, alpha/mip
semantics применяются, DXT/BC в корпусе не найден. По
[ADR-0001](./reference/ADR-0001-runtime-asset-loading.md) оригинальные PC DFF/TXD/BSP читаются в
loading Worker во время runtime; обязательная предварительная конвертация отложена до
подтверждённой profiling-потребности.

### Этап 3. Каркас runtime — 1–2 недели

Прогресс и проверяемые runtime-контракты: [reference/RUNTIME_FOUNDATION.md](./reference/RUNTIME_FOUNDATION.md).

Задачи:

- [x] Fixed-step simulation с шагом 1/60 секунды.
- [x] Раздельные render loop и simulation loop.
- [x] Интерполяция render transforms между physics frames.
- [x] State machine: boot → loading → menu → race → results.
- [x] Унифицированная система событий между core, audio и renderer.
- [x] Debug overlay: FPS, frame time, physics time, draw calls, bodies и contacts.
- [x] Debug camera и отображение Rapier colliders.
- [x] Seeded random generator для игрового core.

Критерий готовности:

- Симуляция не зависит от частоты монитора.
- При 30, 60 и 120 Hz один replay приводит к одинаковому результату.
- Потеря фокуса или длинный кадр не вызывает «взрыва» физики.

Статус 2026-08-23: **этап 3 завершён**. Чистое ядро выделено в `@mashed/core`, запись
input frames — в `@mashed/replay`, Rapier/Web Audio/Three.js подключены через отдельные адаптеры.
Replay с одним seed и input tape даёт побитово одинаковое итоговое состояние при synthetic
presentation clocks 30/60/120 Hz. Catch-up ограничен восемью шагами, потерянное время учитывается
в telemetry, а focus/visibility transitions сбрасывают presentation clock. Browser smoke подтвердил
WebGL/WASM boot, весь state flow, остановку simulation в results, debug camera/colliders и отсутствие
ошибок консоли. Loading Worker разбирает DFF/TXD/BSP и возвращает typed arrays как transferables.

- [x] Поверхности с разным сцеплением: асфальт, лёд, песок и грязь.
- [x] Столкновения стен, динамических и разрушаемых объектов.
- [ ] Столкновения машина–машина.
- [x] Reset/recovery при перевороте или застревании.
- [x] Chase camera.
- [ ] Общая multiplayer camera.
- [x] Параметры машины в data-файлах, а не в коде.

Метод настройки:

- Проводить одинаковые игровые сценарии в оригинале и ремейке.
- Сравнивать разгон, торможение, поворот, занос и реакцию на удар человеческим игровым тестом.
- При необходимости сохранять input sequence или короткое видео конкретного расхождения.

Критерий готовности:

- Машина проходит полный круг без специальных debug-команд.
- Управление предсказуемо с клавиатуры и аналогового стика.
- Столкновения не дают постоянных тоннелирований и неконтролируемых выбросов.
- Тестовый replay детерминирован на поддерживаемых браузерах.

Gate C — физика должна уже ощущаться как аркадная Mashed. Если нет, следующая работа посвящается физике, а не контенту.

Статус 2026-08-24: **этап 4 начат, Gate C открыт**. Реализован первый интерактивный срез:
data-driven chassis, compound colliders, четыре ray-cast колеса, полный базовый ввод,
surface-aware grip, ручник, стабилизация/recovery и chase camera. Тестовая арена позволяет сразу
сравнивать асфальт, лёд, песок и грязь. Второй срез добавил воспроизводимые acceleration/braking/
slalom/drift-метрики, динамические и разрушаемые props и runtime binding parsed `COLLIDE.BSP` в
Rapier trimeshes. Следующий приоритет — замеры против оригинала, track spawn/полный круг и
столкновение двух машин.

### Этап 5. Вертикальный срез — 4–6 недель

Содержание vertical slice:

- одна законченная трасса;
- четыре выбираемых автомобиля;
- 1–4 локальных игрока;
- клавиатура и несколько gamepads;
- общая камера;
- правила старта, круга, финиша и выбывания;
- минимум три оружия или power-up;
- damage/knockback и базовые эффекты;
- HUD, pause и results screen;
- звук двигателя, столкновений, оружия и UI;
- один игровой режим, предпочтительно стандартный battle/race loop.

Критерий готовности:

- Четыре человека могут сыграть несколько полных матчей без перезагрузки страницы.
- Нет blocker-багов за 30 минут игры.
- На целевом компьютере поддерживается 60 fps при 1080p.
- После первой загрузки матч запускается без сетевых запросов к игровым данным.

Milestone M1: публично показываемый proof of concept.

## 6. Quality gates и технические бюджеты

### Correctness

- Fixed timestep: 60 Hz.
- Игровая логика не читает wall-clock time напрямую.
- Каждое изменение физики проверяется хотя бы одним сохранённым replay.
- Парсеры всегда проверяют bounds, sizes и magic values.
- Неподдерживаемый chunk не должен приводить к silent corruption.

### Performance

Стартовые бюджеты, уточняемые после vertical slice:

- 60 fps при 1080p на среднем desktop GPU.
- Physics step p95 не более 4 ms.
- Render CPU p95 не более 8 ms.
- Отсутствие аллокаций в основных per-frame hot paths.
- Трассы и аудио загружаются по требованию.

### Delivery

- Initial shell загружается отдельно от игровых данных.
- Подготовленные данные имеют versioned manifest.
- Импорт можно повторить без ручной очистки браузерного storage.
- В репозитории и публичных artifacts отсутствуют оригинальные ресурсы.

## 7. Тестовая стратегия

- Unit tests для binary readers, chunk boundaries и manifest migrations.
- Синтетические fixtures для общих форматов; hashes вместо публикации оригинальных файлов.
- Golden metadata tests для локально доступных оригинальных ресурсов.
- Replay tests для физики и правил матча.
- Screenshot diff для asset viewer и фиксированных камер.
- Playwright smoke-tests в Chromium, Firefox и WebKit.
- Performance scene с четырьмя машинами, projectiles и максимальным числом эффектов.
- Ручные игровые сессии на нескольких моделях gamepad.

## 8. Основные риски

| Риск | Вероятность / влияние | Как снижаем |
|---|---|---|
| Неизвестный формат BSP | Высокая / критичное | Asset spike до разработки игры; анализ loader-функций `MFL.exe`; отдельный конвертер |
| Физика не похожа на оригинал | Высокая / критичное | Ручные сравнительные сессии, точечные записи расхождений, replay harness, data-driven tuning, отдельный physics gate |
| Несовместимые RenderWare extensions | Средняя / высокое | Chunk inspector, graceful fallback, сравнение с `librw` и существующими parsers |
| Слишком большой объём контента | Высокая / высокое | Vertical slice и подключение трасс пакетами |
| Различия gamepad mapping | Высокая / среднее | Экран назначения кнопок, профили, reconnect tests |
| Память браузера и длинные загрузки | Средняя / высокое | Streaming, Workers, OPFS, KTX2/Opus, lazy loading |
| Права на оригинальные данные | Средняя / критичное | Пользовательский импорт, отсутствие assets в репозитории, проверка до публичного релиза |
| Scope creep: online/mobile/modding | Высокая / высокое | Явно держать вне MVP и возвращаться после beta |

## 9. Что не входит в MVP

- Online multiplayer и rollback netcode.
- Mobile touch controls.
- Split-screen.
- VR/WebXR.
- Редактор трасс и полноценный mod SDK.
- Побайтовое совпадение с оригинальной физикой.
- Поддержка произвольных версий Mashed до стабилизации Fully Loaded Europe.
- WebGPU-only эффекты.

## 10. Порядок принятия решений

1. Сначала extraction.
2. Затем BSP и материалы.
3. Затем физика одной машины.
4. Затем полный матч на одной трассе.
5. Только после этого масштабирование контента и UI.
6. Доставка пользовательских данных и PWA — после доказанной игры.
7. Online multiplayer рассматривается после стабильной beta.

Если любой gate не пройден, мы обновляем оценку и устраняем риск до расширения scope. Количество написанного кода само по себе не считается прогрессом; прогрессом считается работающий проверяемый milestone.

## 11. Ближайшая контрольная точка

**M0: Asset feasibility**

Готово, когда одновременно выполнены четыре условия:

1. Образ извлекается одной командой.
2. `Wildfire` отображается в браузере с текстурами.
3. `Warzone` отображается как сцена.
4. Коллизия `Warzone` совпадает с видимой дорогой.

До M0 разработка меню, прогрессии, AI и полного списка оружия не начинается.
